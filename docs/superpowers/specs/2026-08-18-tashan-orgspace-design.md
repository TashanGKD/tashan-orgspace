# Tashan OrgSpace 产品与技术总设计

> 日期：2026-08-18
> 产品名：Tashan OrgSpace / 他山组织空间
> 仓库：`tashan-orgspace`
> CLI：`torg`
> Web：`https://org.tashan.chat`
> API：`https://api-org.tashan.chat`
> Codex Skill：`tashan-orgspace`
> 状态：用户已于 2026-08-18 批准书面规格；实施须按分阶段计划执行

## 1. 一句话定义

Tashan OrgSpace 是一个以组织为核心、同时提供个人空间的协作与安全计算平台。真实人员使用账号和密码登录，通过 Web、CLI 或调用 CLI 的 AI，以本人身份管理文件、任务、OKR、审批、会议、聊天、通知和服务器运行资源。

平台不是 TopicLab 的新 CLI，也不是现有认知平台中的一个模块。它拥有独立仓库、独立后端、独立 CLI、独立 Web、独立 Skill 和独立部署生命周期。

## 2. 问题本质与产品原则

会议需求的共同本质不是“再做一个待办工具”，而是组织工作信息的四段闭环：

1. **收集**：文件、群聊消息、会议、任务、申请、通知进入组织系统。
2. **组织**：信息被归入组织、空间、项目、流程、责任人和时间线。
3. **分发**：系统通过个人工作台、群聊、CLI、Web 和短信把信息送到正确的人。
4. **执行与追责**：任务、审批、程序和服务在权限边界内执行，并留下可核查记录。

不可放宽的产品原则：

- 一个真实人员对应一个平台账号；多台机器使用多个设备 token，不用“子账号”模拟设备。
- 所有组织工作均归属于组织；个人视图只是对本人责任的投影，不另造一套事实。
- Web、CLI 和未来 AI 使用同一组服务端能力与权限规则。
- **所有用户功能必须有 CLI 覆盖；CI 强制检查，不靠人工记忆。**
- 默认私密、默认安全、默认不覆盖、默认不执行破坏性操作。
- 任何运行中的代码只能访问被授权的个人或组织空间，不能跨空间、跨组织或接触平台控制面。
- 公网出站允许，但私网、宿主机、控制面、云元数据和其他租户网络必须阻断。
- 所有短信使用阿里云短信；业务层负责幂等、重试、回执和审计。
- v1 不实现 AI 员工，但身份、权限、事件、会话和审批模型不得把未来 AI 排除在外。

## 3. 范围边界与拆分

平台过大，不采用一次性“大爆炸”交付。总设计固定跨子系统契约，具体实现按独立规格推进。

### 3.1 v1 业务范围

- 账号、密码、手机号验证、设备 token、组织与成员。
- 个人空间和组织空间；文件上传、下载、读取、搜索和回收站。
- 组织 OKR、个人 OKR、任务、会议记录、通用审批。
- 站内通知、阿里云短信和提醒策略。
- 单聊、组织群聊、附件、搜索、已读状态和消息转工作项。
- Python、Node.js、编译型语言、Docker 构建、批处理任务。
- 长期 Web 服务、数据库和 Agent daemon 等常驻进程。
- 自动 HTTPS 域名、默认登录保护和显式匿名公开。
- Web、CLI、独立 Codex Skill、能力清单与审计。

### 3.2 v1 明确不做

- 不实现 AI 员工、AI 自动审批或 AI 自主执行组织决策。
- 不实现报销、项目申请的专属业务字段，只提供可扩展的通用流程内核。
- 不自建音视频会议网络，只记录会议并为未来会议提供商适配器预留接口。
- 不做跨组织私聊；v1 单聊双方必须至少共同属于一个组织，并明确选择归属组织。
- 不开放用户直接使用宿主机 Docker socket、宿主机 shell 或任意端口映射。
- 不把已安装的阿里云短信 shell Skill 当成生产短信发送引擎。

### 3.3 后续独立规格

1. 平台骨架、认证、组织、设备与审计。
2. 空间、对象存储、配额和文件 CLI。
3. Work Item / Process / Assignment 协作内核与 OKR。
4. 通知、阿里云短信和定时提醒。
5. 聊天、实时事件和消息转工作项。
6. 运行时、构建、任务、服务、数据库与网络隔离。
7. 动态 HTTPS 入口与服务公开策略。
8. Web 全工作台与独立 Codex Skill。
9. AUP 生产部署、备份、恢复、监控和安全加固。

每个子系统必须单独完成设计、实现计划、威胁测试和验收，不能以本总设计替代实施规格。

## 4. 身份、组织与设备

### 4.1 核心身份对象

- `Account`：真实人员的全局账号，保存登录名、密码摘要、已验证手机号和状态。
- `Principal`：所有可授权行为主体的统一抽象。v1 类型为 `human` 和 `system`；预留 `ai_employee`、`service_account`。
- `Organization`：组织本体、状态、默认策略和 500 GB 空间额度。
- `Membership`：某账号在某组织中的唯一成员身份，含角色与状态。
- `Device`：账号的一台逻辑设备，保存稳定设备 ID、名称、OS、架构和首次/最近活动时间。
- `Session`：某设备的一次登录会话，关联可撤销 refresh token、IP 和客户端版本。

同一账号可以加入多个组织。`Membership` 不复制账号手机号；组织需要发送短信时读取账号当前已验证手机号。没有已验证手机号的账号不能激活任何组织 Membership。变更手机号必须重新验证，并使旧号码停止接收后续消息。

### 4.2 登录与 token

- `torg auth login --username <name>` 通过终端安全提示输入密码；不提供明文 `--password` 参数。
- 无交互环境只允许 `--password-stdin`，并明确提示调用方避免日志记录标准输入。
- 密码使用 Argon2id 摘要；服务端不保存明文。
- access token 短时有效；refresh token 绑定设备、可单独撤销并定期轮换。
- macOS 保存到 Keychain；Linux 使用 Secret Service。安全存储不可用时默认只保留内存会话；只有用户显式指定凭据文件并提供加密口令，才写入权限为 `0600` 的加密文件。
- 本地 AI 调用 `torg` 时直接复用用户登录后的设备 token，以用户本人身份操作；AI 不是另一个成员。
- 每次敏感请求同时校验账号、成员状态、设备状态、token 版本和组织状态。

### 4.3 角色与授权

平台级：

- `platform_superadmin`：平台运维、组织配额、弹性资源与 break-glass。
- `platform_operator`：限定运维能力，不自动获得业务数据读取权。

组织级：

- `org_owner`：组织所有权与管理员管理。
- `org_admin`：成员、任务、OKR、流程和组织空间管理。
- `member`：普通成员，可创建和指派任务、发起审批、参与聊天和使用被授予空间/算力。

管理员权限不是万能后门。个人空间不对组织管理员开放；平台 break-glass 必须填写理由、限定对象和时间，形成高风险不可篡改审计，并通知数据本人。

## 5. 审计与设备可观测性

每个可记录的操作生成结构化 `AuditEvent`：

- 账号、Principal、组织、Membership。
- session、device ID、设备名、OS、架构、CLI/Web/Skill 版本。
- 服务端观察到的源 IP、可信代理链、粗粒度网络归属；不信任客户端自报 IP。
- capability ID、对象类型、对象 ID、动作、结果和错误码。
- 请求 ID、幂等键、时间、耗时、入口渠道和 user-agent。
- 变更前后字段摘要；敏感字段只记录掩码或不可逆摘要。
- AI 调用时记录 `actor_source=ai_via_cli`，仍以用户 Principal 授权。

普通安全审计默认保留 365 天；短信发送账本默认保留 3 年。break-glass、合规读取、角色变更、永久删除和服务公开等高风险审计在组织存续期内不自动清理，组织关闭后继续保留 3 年。组织可配置更长时间。审计日志追加写入，普通管理员不能修改或删除；导出与查询本身也进入审计。

## 6. 空间、文件与配额

### 6.1 空间类型

- 每个账号一个 `personal` 空间，默认 50 GB。组织管理员可为本组织成员签发更高的个人额度 entitlement，平台绝对上限为 500 GB；用户同时属于多个组织时取所有有效 entitlement 的最大值。成员离开签发组织后该 entitlement 失效；若实际用量已高于新上限，空间转为只读但不自动删除数据。
- 每个组织一个 `organization` 空间，额度固定为 500 GB，与成员个人空间相互独立。
- 个人空间仅本人可访问；组织管理员没有继承访问权。
- 组织空间默认组织成员可读，写入由角色与路径 ACL 控制；受限项目可建立受限目录。

### 6.2 文件模型

文件元数据进入 PostgreSQL，内容进入 S3 兼容对象存储。关键对象：

- `Space`、`FileEntry`、`FileVersion`、`UploadSession`、`StorageReservation`、`TrashEntry`。
- 路径是用户界面，不是底层授权边界；授权基于不可猜测对象 ID 与 `space_id`。
- 上传采用分片、断点续传、内容校验和服务端最终校验。
- 上传前事务性预留配额；完成后转为实际占用；失败或超时必须释放预留和临时分片。
- 回收站中的内容继续占用配额，直到过期清理或显式永久删除。
- 同名上传默认失败；必须显式选择新版本或覆盖，且覆盖仍保留可恢复版本。
- 下载、读取和搜索不限定文件类型；不设置独立的单文件大小与下载次数限制，只受空间配额、系统保护和合理的并发控制约束。

### 6.3 文件安全

必须先写拒绝测试，再写正常路径：

- `../`、绝对路径、Unicode 混淆、URL 编码穿越。
- 符号链接、硬链接、前缀碰撞和挂载点逃逸。
- 上传中断、校验和错误、配额并发超卖和临时对象泄漏。
- 跨组织对象 ID、猜测文件 ID、失效分享链接和越权版本读取。

运行时挂载只通过平台解析后的空间卷，不能将用户字符串直接拼成宿主机路径。

## 7. 统一组织工作内核

### 7.1 为什么采用统一内核

任务、会议、审批、报销、项目申请的共同规律是：某个组织事实被创建，经过一个可版本化流程，被分配给人员或角色，在时间约束内发生状态变化，并产生通知、审计和后续动作。

因此不为每种制度复制一套“待办表”，而采用三类核心对象：

- `WorkItem`：组织事实与当前状态的唯一真源。
- `ProcessInstance`：该事实采用的流程定义、节点和流转记录。
- `Assignment`：某节点对某人/角色产生的责任、审批或知会。

个人待办、组织待办、会议日历和审批箱都是同一组对象的查询投影。

### 7.2 WorkItem

v1 类型：`task`、`meeting`、`approval`、`okr_change_request`。字段包括：

- 归属组织、标题、描述、创建者、当前负责人。
- 状态、优先级、是否紧急、开始时间、截止时间。
- 可见性：`organization` 或 `restricted`。
- 关联文件、聊天消息、OKR、父子工作项和来源对象。
- 当前流程版本和不可变事件序列。

通用任务与会议默认组织内全员可见；受限事项仅参与者、授权角色和管理员可见。管理员可查看全部组织待办，但受限事项的正文读取也必须进入审计。

### 7.3 创建、指派与异议

- 普通成员可以给其他组织成员创建并指派任务。
- 指派提交成功后立即生效，不等待对方接受。
- 被指派人可以提交异议或申请转派；在管理员或创建者处理前，原指派仍有效。
- 创建者可以修改任务定义；负责人可以更新进度和完成状态；管理员可以修改全部字段并处理争议。
- 所有转派、驳回、完成和重新打开均记录理由与事件。

### 7.4 ProcessDefinition

流程定义版本发布后不可原地修改；新制度创建新版本，运行中的实例继续使用启动时版本。节点统一支持：

- 人员、角色或未来 AI Principal 执行。
- 单人审批、多人会签、任一通过、顺序审批。
- 超时、提醒、退回、转派、撤回和管理员干预。
- 条件分支、表单 schema、附件要求和事件回调。

未来报销、项目申请和在线会议以领域扩展包加入：扩展包定义表单、校验器、流程模板和展示，不复制身份、权限、通知和审计基础设施。

## 8. OKR

层级为组织 Objective → 组织 KR → 个人 Objective/KR → 任务与工作项。个人 OKR 必须归属于组织，不存在组织外的私人 OKR。

权限规则：

- 组织内所有成员可查看所有成员的 OKR。
- 组织级 Objective/KR 只有组织管理员可以创建或实质性修改；成员可以评论、更新获授权指标和关联任务。
- 只有 OKR 本人和组织管理员可以提出修改。
- 进度更新立即生效并保留历史。
- 目标、指标、权重、计算方式和周期等实质性修改生成 `okr_change_request`，必须由管理员批准后生效。
- 管理员本人做实质性修改可直接生效，但仍生成等价审批事件以保留审计轨迹。

KR 支持三种计算方式：

- `numeric`：当前值/目标值自动计算。
- `linked_tasks`：根据关联任务及权重自动计算。
- `manual`：本人更新进度并填写说明。

每次计算保存输入快照和公式版本，避免以后公式变化导致历史进度不可解释。

## 9. 通知与阿里云短信

### 9.1 通知矩阵

| 事件 | 站内通知 | 短信 | 能否关闭 |
|---|---:|---:|---:|
| 新审批请求 | 立即 | 立即 | 不能 |
| 明确标记为紧急的通知 | 立即 | 立即 | 不能 |
| 紧急聊天消息 | 立即 | 立即 | 不能；发送者必须填理由且受频控 |
| 普通任务创建 | 立即 | 默认不发；创建者可选 | 可选择本次发送 |
| 未完成任务截止前 1 小时 | 立即 | 立即 | 不能 |
| 会议开始前 1 小时 | 立即 | 立即 | 不能 |
| 每日汇总 | 每日 | 默认发送 | 成员可以关闭 |

“只能取消每日汇总”是强约束。成员不能关闭审批、紧急、DDL 和会议提醒。

每日汇总按组织时区在组织统一设置的时间发送，v1 默认 09:00；成员只能选择是否接收，不能各自改变发送时间。DDL 与会议提醒也以组织时区保存和计算，API 同时保存 UTC 时间，避免夏令时和跨时区重复提醒。

### 9.2 生产短信架构

- 所有短信使用阿里云短信 SDK，由 `NotificationWorker` 调用，不通过 shell。
- 独立 RAM role 只授予发送、模板/签名查询和送达明细查询所需最小权限。
- 模板分为验证码、审批、紧急、任务提醒、会议提醒和每日汇总；只使用已审核模板与签名。
- 每条短信以业务事件 ID、接收账号、模板和提醒窗口生成唯一幂等键。
- PostgreSQL 事务同时写业务状态和 outbox；Worker 领取 outbox 后发送，保存 RequestId、BizId 和阿里云响应。
- `Code=OK` 只标记 `accepted`，不能标记 `delivered`。Worker 使用 BizId 查询 `QuerySendDetails`，记录 `in_flight / failed / delivered` 和 ErrCode。
- 超时后先查送达明细，再决定是否重试；禁止盲目重发。
- 手机号、短信内容和资质信息在日志中掩码；原始手机号加密保存。

已安装的 `alibabacloud-sms-send-short-message` Codex Skill 用于受控的管理员查询、诊断和人工确认发送。它不进入生产依赖图；任何真实发送必须先明确展示号码、签名、模板、参数和人数并获得确认。

## 10. 聊天

### 10.1 会话类型与边界

- `direct`：双方至少共同属于一个组织，创建时必须选择一个共同组织作为归属。
- `group`：归属于一个组织；组织管理员不自动成为所有群成员。
- 跨组织直接聊天在 v1 拒绝，即使双方分别在其他组织中认识。

消息支持文本、文件、图片、视频、语音、链接、回复、引用、@、表情回应、编辑、撤回、已读和搜索。附件必须位于同一组织空间或复制为该会话授权对象，不能通过消息绕过空间权限。

### 10.2 实时与顺序

- 客户端生成 `client_message_id`，服务端以组织会话维度分配递增 `server_seq`。
- 重发同一 client ID 返回原消息，不能生成重复消息。
- WebSocket 只承担实时分发；历史和缺口通过 HTTP/游标补齐。
- 编辑和撤回是新事件，不覆盖历史事件。
- 被撤回内容从普通 UI 和搜索中消失；加密原文默认保留 365 天，仅合规读取可见。

### 10.3 合规读取

私聊正文默认仅双方可见。组织 owner 发起合规读取时必须：

1. 填写原因、时间范围和目标会话。
2. 通过受限权限检查，不能批量导出整个组织聊天。
3. 生成高风险审计，并通知相关成员。
4. 只有组织明确配置且记录了延迟通知政策时，才允许延后通知；不能永久不通知。

### 10.4 信息转工作

任一消息可以转成任务、审批、会议或组织文件条目。新对象保存来源消息 ID 和不可变摘要；消息保存反向链接。撤回消息不会删除已经创建的工作项，但工作项会显示来源已撤回。

## 11. 计算、构建与常驻服务

### 11.1 支持范围

v1 从第一天支持：

- Python、Node.js、常见编译型语言工具链。
- rootless BuildKit 构建 Docker/OCI 镜像。
- 短任务、定时任务、批处理和交互日志。
- 长期 Web 服务、数据库和 Agent daemon。
- 公网出站访问。

运行对象统一建模为 `RuntimeWorkload`，类型为 `job`、`service`、`database`、`daemon`、`build`。每个对象包含所属组织/个人空间、镜像或构建来源、命令、环境变量引用、资源策略、期望状态和实际状态。

### 11.2 空间边界

- 工作负载启动时必须明确选择一个个人空间或组织空间。
- 只挂载该空间授权目录以及只读运行时镜像；不挂载其他空间、控制面目录或宿主机用户目录。
- secret 使用独立 secrets store 以文件或短期环境注入，不写入镜像、日志或工作空间。
- 数据库数据卷归属同一空间，计入该空间额度。
- 数据库只能由同一空间授权工作负载或经平台代理的获准客户端访问，默认无公网端口。

### 11.3 网络边界

允许 DNS、HTTP(S) 和用户明确需要的公网出站，但拒绝：

- IPv4/IPv6 loopback、RFC1918、链路本地、IPv6 ULA。
- AUP 管理网、容器桥接网、平台控制面、其他租户网段。
- 云元数据地址、Docker API、Kubernetes/API 控制地址。
- DNS 首次解析为公网、连接时重绑定到私网的请求。

出口策略在网络层执行，应用层 URL 校验只是第二道防线。平台服务入口仅通过 gateway，用户容器不能自行监听宿主机公网接口。

### 11.4 AUP 资源池

2026-08-18 实机验证基线：32 CPU、约 62.4 GiB 总内存、cgroup v2、Docker 29.1.5、Compose v5.0.1、user namespace 已启用、`rootlesskit` 已存在。`newuidmap/newgidmap` 当前缺失，执行器上线前必须安装并验证 rootless 容器；禁止向用户暴露当前 rootful Docker socket。

初始资源池：

- 平台与操作系统保留：1 CPU、10 GiB 内存。
- 应急保留：1 CPU、4 GiB 内存。
- 用户计算池：30 CPU、48 GiB 内存。

资源策略：

- `capped`：默认，设置 CPU、内存、进程数、临时盘和运行时长上限。
- `elastic`：可使用用户池中当前空闲资源，但永不侵占平台和应急保留。
- 组织管理员只能在平台授予该组织的预算内调整成员上限。
- 只有平台超级管理员可授予 elastic；只有超级管理员或指定应急调度器可使用应急池。
- cgroup v2、cpuset、pids 和临时盘配额机器强制执行，不能只写在数据库字段中。

## 12. 自动 HTTPS 服务

### 12.1 域名和可见性

用户服务获得：

`https://<service>-<space>.tashan.chat`

slug 必须全局唯一，保留平台关键字，并对 Host header 做严格规范化。新服务默认 `private`：域名公网可达，但 gateway 要求平台登录并校验空间权限。

```text
torg service public <service-id> --space <space-id>
```

该命令意味着“互联网上任何匿名用户均可访问”，CLI 必须在帮助和确认界面完整显示这句话。恢复：

```text
torg service private <service-id> --space <space-id>
```

### 12.2 动态入口架构

```text
Browser / CLI
  -> wildcard *.tashan.chat on ECS
  -> ECS wildcard TLS + Nginx
  -> one persistent reverse tunnel
  -> AUP platform gateway
  -> auth + dynamic host/service lookup
  -> isolated user runtime
```

不能为每个用户服务人工新增一条 tunnel 和一份 Nginx 配置。ECS 只维护平台级 wildcard 入口和持久隧道；AUP gateway 根据标准化 Host 查询 service registry，再代理到动态运行时。

## 13. 系统架构

### 13.1 Monorepo

```text
tashan-orgspace/
  apps/
    web/           React Web 工作台
    api/           Fastify 控制面 API
    worker/        outbox、短信、提醒、清理与调和
    realtime/      WebSocket、聊天和事件分发
    cli/           Node.js/TypeScript CLI: torg
  services/
    gateway/       Go 动态服务入口与访问控制
    executor/      Go AUP 运行时执行器
  packages/
    contracts/     schema、错误码、事件、权限和能力清单
    capabilities/  capability 注册与一致性生成
    sdk/           Web/CLI 共用 TS SDK
  skill/           独立 tashan-orgspace Codex Skill
  deploy/          AUP/ECS 编排、迁移、备份和 runbook
  docs/            产品、架构、规格和运维证据
```

### 13.2 基础设施

- PostgreSQL：交易数据、授权、元数据、事件序列和 outbox。
- Redis：短期缓存、分布式租约、频控和实时 fan-out；不是业务真源。
- S3 兼容对象存储：文件、版本、上传分片和构建产物。
- rootless Docker/BuildKit：构建与隔离运行。
- ECS Nginx/TLS：公网入口；AUP gateway：动态服务路由。

### 13.3 组件边界

- API 只处理控制面命令和查询，不直接执行用户程序或发送短信。
- Worker 处理可靠异步任务；所有任务来自数据库 outbox 或可恢复调度表。
- Realtime 不拥有聊天真相；消息先提交数据库，再分发。
- Executor 只接受经过签名、短期有效、绑定空间和资源策略的执行租约。
- Gateway 不信任用户服务上报的身份，自己完成域名解析、登录和授权。

## 14. 能力清单、CLI 与 Web

### 14.1 Capability Manifest

服务端每项用户能力必须注册唯一 capability，至少声明：

- `id`、版本、输入/输出 schema。
- 所需权限和对象作用域。
- 是否有副作用、是否幂等、是否需要确认。
- CLI 命令绑定、JSON 输出和流式输出方式。
- Web surface 状态：`required` 或显式 `deferred`。
- 稳定错误码、审计动作和事件类型。

CLI 与 Web SDK 从该清单和 schema 生成/校验，不能各自手写一份易漂移命令表。

### 14.2 CLI 命令面

- `torg auth ...`、`device ...`
- `torg org ...`、`member ...`
- `torg space ...`、`file ...`
- `torg okr ...`、`task ...`、`meeting ...`
- `torg process ...`、`approval ...`
- `torg notify ...`
- `torg chat ...`、`message ...`
- `torg run ...`、`job ...`、`build ...`
- `torg service ...`、`db ...`
- `torg audit ...`
- `torg capability list|describe --json`

规则：

- 无参数只显示帮助，不登录、不联网、不安装依赖、不执行任何动作。
- 组织写操作必须显式提供 `--org`；所有空间操作必须显式提供 `--space`。组织空间操作同时提供两者，个人空间操作只提供 `--space`。
- 机器调用支持稳定 `--json`、标准错误码和 stdout/stderr 分离。
- `file sync` 默认 dry-run；覆盖、永久删除、公开服务和高风险资源提升必须显式确认。
- 非交互自动化需要同时提供 `--yes` 和幂等键；仅 `--yes` 不能绕过权限或缺失参数。
- 删除默认进回收站；永久删除必须再次确认并写审计。

### 14.3 CI 一致性门禁

CI 必须机器比较：

1. 服务端注册的 capability 集合。
2. CLI command binding 集合。
3. Web surface 声明与已实现路由/动作。
4. Skill 引用的 capability ID。

任一服务端用户能力缺少 CLI 绑定，构建直接失败。Web 可以分阶段实现，但每个缺口必须显式标为 `deferred`，不能静默遗漏。每个一致性 gate 必须有同名 `*.self-test`，构造缺少 CLI、schema 漂移和错误 capability ID 的负例，证明 gate 真能拦截。

Codex Skill 不复制全部命令说明，而是优先调用 `torg capability list|describe --json` 发现当前能力，避免 Skill 与 CLI 漂移。

## 15. 数据一致性与故障处理

- 所有写操作支持请求幂等键；服务端以 actor、capability 和幂等键判重。
- 业务事务与 outbox 同一 PostgreSQL 事务提交。
- Worker 使用租约、心跳、指数退避和死信队列；失败可重放但不能重复产生业务效果。
- 定时提醒保存确定的提醒实例和唯一键，重启后可恢复。
- 上传分片有 TTL 清理；成功对象必须同时满足数据库完成状态和对象校验和。
- RuntimeWorkload 保存 `desired_state` 与 `actual_state`，调和器处理进程崩溃和节点重启。
- 聊天以 client ID 去重、server seq 排序；WebSocket 断线通过游标补齐。
- 审批节点使用版本号/乐观锁，重复点击只能有一个状态转换成功。

外部服务超时不等于失败。短信、对象存储和运行时创建都先查询实际状态，再决定补偿或重试。

## 18. AUP 与 ECS 运维设计

### 18.1 管理与用户链路分离

- 运维可通过本机 SSH alias `aup-server` 经 Tailscale 登录 AUP；该入口只用于部署和排障。
- 最终用户和 AI 不获得 AUP SSH；只访问 `api-org.tashan.chat` 并使用用户 token。
- 公网服务经 ECS wildcard TLS、平台级持久隧道和 AUP gateway。
- `*.tashan.chat` 已有 wildcard DNS，但生产前仍要以 ECS 生效 Nginx、证书和公网请求为准。

### 18.2 上线前硬门槛

- 安装 `newuidmap/newgidmap` 并完成 rootless Docker/BuildKit 负例验证。
- 定义平台、应急、用户 cgroup 树并证明保留资源不能被用户任务侵占。
- 禁止 executor 访问 rootful Docker socket。
- 建立 PostgreSQL、对象存储和 secret 的备份恢复演练。
- 建立一条持久、可监控、自恢复的 ECS↔AUP 隧道。
- 动态 gateway 上线前先在专用测试域名验证 Host 隔离和默认登录保护。
- 运维文档记录端口、域名、证书、systemd 单元和回滚；真实密钥不进入 Git。

## 20. v1 验收定义

只有同时满足以下条件，才能称为 v1：

- 两名真实用户能从两台以上设备登录、撤销单个设备并切换共同组织。
- 能在个人和组织空间完成大文件断点上传、校验、下载、回收和配额拒绝。
- 普通成员能指派任务；负责人能异议/申请转派；组织/个人视图一致。
- OKR 进度即时更新，实质性修改必须经过管理员审批。
- 审批、紧急、DDL 和会议短信按规则发送且不可关闭；每日汇总可关闭。
- 单聊必须有共同组织；群聊、附件、撤回、搜索和消息转任务可用。
- Python、Node、编译项目、Docker build、长期服务、数据库和 daemon 均能运行。
- 容器能访问公网，但无法访问其他空间、AUP 控制面、元数据和宿主机服务。
- 用户服务自动获得 HTTPS；默认要求登录；显式 public 后匿名可访问并可恢复 private。
- 服务端所有用户 capability 都有 CLI 绑定，删除任一绑定时 CI 负例能稳定失败。
- 重启 API、Worker、Executor、Gateway 和 AUP 后，上传、提醒、任务和服务能调和恢复且不重复产生副作用。
